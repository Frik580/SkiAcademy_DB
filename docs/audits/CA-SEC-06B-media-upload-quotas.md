## THREAT MODEL

| Сценарий | Результат проверки и остаточный риск |
| --- | --- |
| A. Upload flooding | Старый cap ограничивал HTTP-запросы, включая чтение и части, но не число операций публикации за более длинное окно. Новый бюджет ограничивает дорогую обработку и запись. Прямые admin SDK-пути остаются ограничены ролью и размером. |
| B. Storage exhaustion | Новые объекты чата и immutable admin-объекты накапливаются. Бюджет замедляет прирост через шлюзы. Общий объём за срок жизни всё ещё растёт без согласованного retention. |
| C. Oversized uploads | Прежние границы проверяются по фактическим байтам HTTP-тела/объекта. Чат проверяет размер отдельных частей и итоговое ограничение типа. Валидация Functions происходит после получения тела платформой. [Квоты Firebase Functions](https://firebase.google.com/docs/functions/quotas) |
| D. Repeated replacement | Аватары и стандартные каталожные пути сохраняют один текущий объект. Immutable логотипы и QR сохраняют предыдущие версии. Soft delete и versioning могут отдельно удерживать перезаписанные/удалённые поколения. Их настройки и объём требуют проверки. [Cloud Storage soft delete](https://docs.cloud.google.com/storage/docs/soft-delete) |
| E. Orphaned uploads | Из кода подтверждены пути появления сирот без обращения к данным production. В чате пользователь может загрузить вложение и снять его с черновика. Обложка, логотип или QR могут сохраниться до отказа канонической команды. Удаление совмещённого сообщения/вложения отсутствует. Временные объекты ограничены семью текущими слотами, но могут лежать бессрочно. |
| F. Concurrent uploads | Firestore транзакционно проверяет и списывает бюджет на Account и категорию. Один HTTP-запрос записи/публикации/очистки владеет арендой до завершения. Временные слоты остаются общими для upload ID этого Account. |
| G. Account farming | Отдельный авторизованный Account получает отдельный бюджет. Для чата нужен актуальный доступ к треду, для аватара управление Participant, для admin-медиа роль admin. Регистрационный антифрод относится к CA-SEC-06D. |
| H. Cost amplification | Повтор давления на Functions/Auth/Firestore возможен в пределах прежнего admission. Закрыты повторные записи уже сохранённой части или идентичного текущего изображения. Публикация, отмена и проверка прав выполняют ограниченное число операций. Масштабирование по аккаунтам и повторная HTTP-передача остаются отдельными рисками. |

Окна начинаются при первом списании соответствующего ресурса. Каждая из трёх LIVE-категорий допускает один мутирующий HTTP-запрос с действующей арендой на Account. Одна аренда длится до 3 минут при падении процесса. Таймаут HTTP не гарантирует остановку уже начавшейся операции Storage. Бюджет списывается до работы, а записи используют условия поколения. [Транзакции Firestore](https://firebase.google.com/docs/firestore/manage-data/transactions)

Идентичный сохранённый чанк или изображение определяются по metadata и серверному SHA-256. Повтор завершённого `finish` не списывает бюджет. Для неуспешной операции аренда освобождается, а уже списанные попытки и байты учитываются, поскольку работа могла произойти. При повторной передаче отсутствующего чанка это новая работа. Удаление файла или частей не пополняет бюджет.

## ROOT CAUSE

Общий HTTP admission ограничивал число запросов, а правила SDK проверяли только данные одного объекта. У этих проверок отсутствовал атомарный учёт суммы байтов и операций публикации. Durable-медиа и временная часть загрузки имеют разные жизненные циклы. Успешная запись в Storage не означает, что каноническая ссылка затем сохранилась.

## FIX

- После актуальной авторизации серверные HTTP-шлюзы применяют отдельный бюджет записи для LIVE. Ключ определяется по проверенному токену и серверной категории. Документы недоступны клиенту по Firestore Rules.
- Ограничения объёма/частоты возвращают HTTP 429 с причиной и временем сброса. Конкуренция возвращает 429 с отдельной причиной. UI показывает RU/EN сообщение и снимает индикатор загрузки. Открытый чат при повторном выборе того же файла переиспользует идентификатор и сначала проверяет результат предыдущей публикации.
- Очистка временных частей дожидается всех операций перед освобождением аренды. Ошибка очистки после успешной записи не отменяет результат публикации.

### Принятые риски и отложенная работа

- **Логотипы и QR.** Оба пути требуют совпадения UID в пути с UID сессии и актуального канонического LIVE Account с ролью `admin`. Rules исключают TEST-актора и обычного пользователя, даже при наличии admin claim без серверной роли. Разрешены только новые immutable объекты ненулевого размера с declared MIME `image/png`, `image/jpeg` или `image/webp`. Положительные и отрицательные проверки покрывают ограничения обоих путей. Storage Rules видят MIME из метаданных объекта. Проверка байтов и накопительная квота на создание объектов для доверенных администраторов остаются отложенными, включая риск злоупотребления скомпрометированным admin Account. [Условия Cloud Storage Rules](https://firebase.google.com/docs/storage/security/rules-conditions)
- **Хранение.** Семь текущих слотов на Account ограничивают временный LIVE-префикс. Исторические поколения и постоянные объекты могут накапливаться. Предлагаемые сроки, сверка ссылок, dry run и условия запуска вынесены в [отдельную задачу по хранению](./CA-SEC-06B-media-retention-followup.md).
- **Входящий трафик.** Квота байтов применяется к новой работе со Storage. Повтор передачи HTTP-тела ограничивается действующим request admission. Распределение нагрузки по нескольким аккаунтам и работа, пережившая срок аренды, остаются ограничениями выбранной модели.

Источник роли для Storage Rules — `users/{uid}`. Firestore Rules разрешают клиентский bootstrap только с ролью `user` и исключают изменения канонической роли и lifecycle из self-service. Существующий тест `allows safe self-service fields but blocks self-promotion` закрепляет запрет повышения роли.

## PERFORMANCE

| Путь | До | Добавилось на запрос, без повторов Firestore |
| --- | --- | --- |
| Новая запись изображения | 1 read + 1 write admission, текущие проверки auth и metadata | 3 reads + 3 writes (аренда, списание, освобождение), SHA-256 ≤5 MiB |
| Новый чанк чата | 1 read + 1 write admission, текущая ACL, запись части | 3 reads + 3 writes, одна проверка Storage metadata и SHA-256 ≤8 MiB |
| Новая публикация чата | 1 read + 1 write admission, текущая ACL и обработка частей | 3 reads + 3 writes, прежний предел до 7 частей |
| Повтор сохранённой записи / `DELETE` | Прежние admission и ACL | 2 reads + 2 writes; повтор чанка пропускает его Storage write. `DELETE` проверяет до 7 объектов. |
| Проверка результата при ручном повторе | Клиент начинал новую загрузку | Один HTTP-запрос с прежним admission и ACL, один Storage metadata lookup, без операций с документом квоты. Если результат ещё не появился, каждый повторно отправляемый чанк делает ещё один metadata lookup под арендой перед списанием |
| Отказ по занятой аренде / исчерпанному бюджету | — | 1 read без записи / 3 reads + 2 writes. При отказе на `finish` сохраняется ограниченная очистка. |
| Чтение медиа, SDK и TEST | Прежние проверки | 0 новых Firestore reads/writes |

У обычного вложения чата из одной части добавляется 6 reads + 6 writes, у видео из семи частей 24 + 24. У нормальной загрузки число HTTP-вызовов прежнее (один для изображения, `N+1` для чата); отдельный вызов нужен лишь при ручном возобновлении после ошибки. Задержка включает последовательные round-trip транзакций и, для чанка, metadata lookup. Замеры p50/p95 в production отсутствуют.

Счётчик вызовов SDK в эмуляторе выделяет только документ квоты данного Account. Новый чанк и новый `finish` дают по **3 reads + 3 writes**. Захват аренды сериализует операции над общими слотами. Списание привязано к действующей аренде и выполняется после проверки, нужна ли новая работа в Storage. Освобождение сверяет ID владельца аренды, чтобы поздний ответ не освободил чужую аренду. Все три операции выполняют отдельную защитную проверку в принятой реализации. Объединение этапов потребует заново проверить границу между Firestore и Storage, ошибки и повторы.

Тот же тест измеряет **0 + 0** дополнительных операций квоты для скачивания и `checkOnly`, **2 + 2** для повторного `finish` (аренда и освобождение). После этих запросов счётчики сохраняют ровно один размер принятого чанка и одну публикацию. Отдельные регрессии проверяют идентичный чанк, повтор после потерянного ответа и конкурентный отказ.

## COST IMPACT

Законная новая загрузка добавляет транзакции. Отказы до дорогой операции и повторы уже записанных объектов уменьшают число записей и обработок Storage. Повтор одного запроса к Storage-шлюзу по-прежнему доставляет HTTP-тело и потребляет существующий request admission. Цена egress и чтения публичных объектов остаётся зависимой от запросов к ним.

Firestore использует максимум три документа квот на активный Account, без массивов upload ID и глобального счётчика. Конкуренция сосредоточена на Account и категории. При высокой конкуренции транзакционные повторы увеличивают число чтений. Каждый документ получает `deleteAt` на 24 часа вперёд, используется существующая TTL-конфигурация `security_request_limits.deleteAt`. Фактическая очистка асинхронна и тарифицируется. Полных сканов, drain, polling и schedulers нет. [Firestore TTL](https://firebase.google.com/docs/firestore/ttl)

Это применимо к обычному изображению и видео, сжатому интерфейсом до 800 KiB. Для тысячи семичастных видео верхней границы тот же расчёт даёт **$0.0576**. Фактические скидки, налог, остаток бесплатной квоты, число транзакционных повторов и production SKU не измерялись. ## STAGING SMOKE

1. Под отдельным разрешением использовать только проект `ski-school-staging` и выделенные тестовые Account. Сверить развернутую базу CA-SEC-06A, запрет прямой записи в пути шлюзов, Firestore TTL `security_request_limits.deleteAt` и статус исторических bearer URL на staging. Если действующие исторические ссылки остались или базовые Rules отличаются, остановить этап и согласовать исправление. Production-результат исторической инвентаризации на staging не переносится. [Чеклист исторических ссылок](../operations/booking-chat-media.md)
2. Подготовить Functions и Hosting артефакты из одобренной ревизии посредством `npm run build:functions` и `npm run build:staging`. После разрешённого выката сверить ревизии двух Functions и Hosting. Записывать код ответа, роль и длительность, сохраняя токены и URL вне отчёта.
3. Войти учеником и инструктором с актуальным доступом, отправить JPEG и короткое видео, открыть чат после перезагрузки и проверить воспроизведение. В открытом чате повторно выбрать файл после потерянного ответа на публикацию и подтвердить один объект по тому же пути. Войти посторонним Account и проверить отказ шлюза. Проверить аватар своего Participant, отказ для чужого Participant, и замену тестового изображения курса или инструктора администратором.
4. Если тестовые записи разрешены, загрузить черновой логотип и QR через действующий SDK от активного администратора. Проверить отказ для обычного Account. Проверить чтение уже настроенного публичного QR и запрет чтения нового черновика для гостя через SDK. Проверка использует тестовые файлы и существующую конфигурацию оплаты. Причины и локализацию 429 проверить на разрешённой изолированной fixture у границы квоты, используя один запрос на сценарий. Сравнить длительность первого и прогретого вызовов с baseline.
5. Сохранить результат smoke отдельно от статуса исходников. Любой неожиданный успех запретной операции, дубликат итогового объекта или потеря сообщения останавливает выпуск.

## ROLLBACK

При необходимости сначала вернуть предыдущую Hosting-сборку, затем предыдущие ревизии двух HTTP-функций. Старые клиенты продолжают читать новые объекты по непрозрачным URL. Документы квот истекут по существующему TTL. Откат не требует удаления объектов или изменения Rules, индексов и исторических данных.
