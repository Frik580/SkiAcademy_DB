## CURRENT ARCHITECTURE

Firebase Hosting переписывает `/api/img` на HTTP-функцию `optimizeImage` Gen 2. Браузер и CDN первыми проверяют свой кэш. При обращении к функции Admin SDK читает производный объект из default Firebase Storage. При промахе функция проверяет глобальную квоту в Firestore, анонимно загружает публичный источник из Yandex Object Storage, кодирует WebP в sharp и публикует его в Firebase Storage. Storage Rules разрешают публичное чтение `image-cache/{fileName}` и закрывают запись из клиента. [Hosting rewrite](../../firebase.json#L115) [Storage Rules](../../storage.rules#L132)

## ROOT CAUSE

В Storage ключ включал пользовательское качество и исходное представление адреса. Проверка кэша, учёт квоты и публикация были независимыми операциями. HTTP TTL управлял повторной выдачей, а жизненный цикл Storage был отдельной операционной задачей. Политика параллельности функции опиралась на общий лимит по минуте, который сам по себе не ограничивал память экземпляра.

## FIX

- Канонический URL сохраняет регистр ключа, нормализует percent-encoding и исключает неоднозначные декодированные сегменты, backslash и управляющие символы. Источники с query, fragment или подписью отклоняются до Storage. Ключ хранит хеш, а метаданные новых объектов содержат прежние поля и только канонический неподписанный source URL.
- DNS lookup передаёт TLS-сокету только публичные IPv4 и глобальные IPv6 адреса. Частные, loopback, link-local, metadata, multicast, зарезервированные и IPv4-mapped IPv6 адреса исключены. Каждый новый сокет использует проверенный результат lookup с TLS hostname verification. На каждом редиректе сверяются схема, хост, бакет и отсутствие подписи. Все hops используют один 10-секундный дедлайн.
- Входные JPEG, PNG, WebP, GIF и AVIF распознаются по сигнатуре. Внешний `Content-Type` не выбирает обработчик и не копируется в ответ. Неожиданный формат возвращает 415, ошибка декодирования или pixel gate 422, превышение 8 МиБ 413, upstream ошибка 502. Эти ответы `no-store`. В лог backend-ошибки записывается фиксированное сообщение.
- Один Storage GET заменил HEAD-подобную проверку плюс GET. Одинаковые запросы разделяют выполняющееся обещание в экземпляре. Первая распределённая аренда объединена с допуском в одной транзакции. WebP публикуется одним условным upload без внешнего цикла повторов SDK. `ifGenerationMatch: 0` предотвращает перезапись, а 412 возвращает уже опубликованный объект. Локальный предел ожидания загрузки до 5 с. Принятый Storage запрос может завершиться после локального тайм-аута, поэтому порядок первой публикации задаёт Storage, а исходный URL должен быть неизменяемым. [Cloud Storage preconditions](https://cloud.google.com/storage/docs/request-preconditions)
- `concurrency: 4` и один активный холодный путь на экземпляр. Оставшиеся запросы могут получить попадания или разделить обработку того же ключа. Для отдельного холодного ключа при занятости есть быстрый 503 либо браузерный 307. В sharp сохранены 40 Мп и effort 4, добавлены до 8 с обработки libvips, высота до `2 × width` и один кадр при текущих настройках sharp. Платформенный тайм-аут HTTP составляет 60 с.

## CACHE POLICY

Четыре ширины 480/960/1280/1920, одна выходная настройка WebP q72, максимум **4 новых объекта на канонический исходник**. Реальные вызовы передают 960/1920 для hero, 960 для каталога курсов и 1920 для фона Journey. Все используют качество 72. Остальные поддерживаемые ширины сохранены для уже выпущенных клиентов. Целые `q` из прежнего диапазона 40–90 остаются валидными и сводятся к q72. Старые q72-объекты по каноническим URL используются повторно. Редирект на другой canonical key может отдать WebP клиенту и CDN с прежним HTTP TTL, без создания дубликата в Storage. Старые объекты сохраняются.

Дата изменения или generation источника не входит в URL автоматически. Для новой версии изображения нужен новый путь или имя объекта. Действующий CDN хранит успешные ответы до 7 дней и может отдавать stale до суток при revalidation. CDN различает исходные query strings, даже если они ведут к одному объекту Storage. Попадание в CDN завершает запрос до Functions. Storage hits обходят Firestore. [Firebase Hosting cache](https://firebase.google.com/docs/hosting/manage-cache)

Для отдельного согласования предлагается оценить возраст и размер объектов строго в `image-cache/`, использование прямых Storage URL и эффект soft delete. После dry run согласовать окно удаления производных объектов, например 90 дней с даты создания. TTL не должен затронуть оригиналы и защищённые префиксы. До согласования объём может расти с числом новых публичных исходников. Lifecycle, существующие объекты, метаданные bucket и расписания в рамках задачи не менялись.

## RATE LIMIT POLICY

Порог остаётся 120 допусков на окно 60 с по тому же пути документа. Открывший окно запрос записывает `resetAt`. В той же записи находятся аренды по хешированному имени объекта, срок 65 с, и действующий Firestore TTL. Истёкшие аренды удаляются при следующем допуске. Число записей ограничено объёмом окон, пересекающихся с 65 с, максимум 360 даже у границ окон. Запрос с живой арендой прекращается после чтения. Тёплый экземпляр запоминает подтверждённое исчерпание квоты до `resetAt`, поэтому следующие отказы не читают Firestore. При недоступности Firestore обработка оригинала не начинается. Сбой после допуска оставляет аренду до её истечения.

Используется один document read/write на допущенный cold key без retry. Горячий документ сохраняется. Повторы ключа не списывают квоту, а отказы реже обращаются к Firestore. Поиск документов, pagination, scheduler и drain отсутствуют. Запросы анонимны, пользовательские IP-заголовки для admission не используются. Один посетитель всё ещё может исчерпать квоту оптимизации. При загрузке со страницы того же origin обычный `<img>` в браузере с Fetch Metadata получает некэшируемый 307 на проверенный публичный оригинал. Остальные запросы получают 429/503 и `Retry-After`. Насыщение ingress до обработчика и доставка оригинала зависят от инфраструктуры и браузера. Функция в режиме 307 не загружает и не передаёт исходные байты. Трафик в этом случае тарифицирует Yandex, если превышен его free tier.

### Кэш после выпуска

Текущий клиент передаёт `q=72` и те же ширины. Для канонических исходников имя Storage объекта вычисляется из тех же байтов `URL|width|72|webp`. Прежние `q=40…90` продолжают приниматься и читают q72. Пропущенные `w/q` означают 1920/72. Вариант, который существовал только по старому q или под иной формой исходного URL, может дать один холодный промах на каноническую ширину. Повторные запросы используют опубликованную запись. Для редиректов на другой ключ действуют отдельные ограничения публикации, описанные в CACHE POLICY.

24 ноября 2026 года четыре точечных read-only запроса метаданных существующих production объектов подтвердили полный матч имени до/после и HTTP 200. Байты объектов не читались, прокси не вызывался.

Массовой инвалидации при выпуске не ожидается. Rewrite и клиентские URL остаются прежними, Storage уже содержит проверенные q72 варианты. Отдельные написания сырого запроса могут промахнуться в CDN и попасть в Storage без генерации. Реальное число холодных объектов для кастомных баннеров и прежних нестандартных q зависит от заполненности кэша. Для отсутствующих ключей сохраняется предел 120 допусков за окно 60 с. Prewarm и очистка для выпуска не требуются.

## SECURITY REVIEW

Независимая статическая проверка подтвердила границы источников и раздельную выдачу приватных изображений. Замечания P2 по дублированию Storage при редиректах и повторным попыткам записи исправлены. Повторная проверка этих участков не выявила блокирующих замечаний. Остаточные риски — CDN различает исходные query strings, общий анонимный бюджет может исчерпаться, а browser fallback доступен после входа в обработчик. Штатный клиент не оборачивает URL с токеном. Если токен передать явно в `u`, обработчик отклонит запрос до ключа Storage и не выведет исходный URL. Инфраструктурный access log может записать входную строку запроса до валидации. При смене байтов или публичности нужно публиковать новый путь. Ранее публично доступные версии могут оставаться в кэше.

## ROLLBACK

При отдельном согласовании вернуть весь трафик `optimizeImage` на записанную до выпуска рабочую ревизию штатным релизным процессом. Базовый код `0fb99073` читает прежние q72 ключи и понимает существующие `count`, `resetAt`, `deleteAt`. Его первый допущенный запрос заменит документ прежней формой. Во время смешанного трафика старый обработчик может снять аренды своей записью. После отката проверить готовность функции, GET/HEAD известного q72, Hero и кабинет, затем сравнить ошибки и latency.
