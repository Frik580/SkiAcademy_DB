# CA-SEC-07D-03 — Guest Participant Ownership

## VERDICT

LOCAL READY. Локальное исправление в ветке `fix/ca-sec-07d-03-guest-participant-ownership` от `61dd3bee`. На момент начала работы локальные `main` и `origin/main` указывали на этот коммит. Последний коммит репозитория в GitHub совпал.

## ROOT CAUSE

Гостевое создание CourseEnrollment принимало существующий Participant с состоянием `unmanaged_guest` без подтверждения связи с исходной записью. Credential новой записи одновременно использовался для чтения, заполнения профиля и присвоения Participant через `promote_guest`.

## FIX / BEHAVIOR

- Гость может создать профиль без Account. При повторном использовании тот же серверный валидатор проверяет доказательство от исходного Booking или CourseEnrollment в командах создания урока и курса.
- Браузер хранит указатель на исходную запись и использует существующее хранилище подписанных credentials. Для старых сессий источником также служат уже загруженные гостевые записи, по которым сервер разрешил чтение профиля. После отказа гость может явно выбрать новый профиль и повторно отправить форму.
- Состояние резерва, расписание и сводка оплаты доступны по credential своей записи. Чтение профиля и прогресса повторно использованного Participant требует отдельно подписанного разрешения на чтение, привязанного к Enrollment и Participant. Заполнение такого профиля требует действительного доказательства от исходной записи.

## AUTHORIZATION POLICY

Проверки записи проводят в транзакции. Сервер сверяет HMAC, назначение, подписанный срок, текущую дату окончания исходного курса, идентичность и неизменяемую гостевую атрибуцию исходного ресурса, Participant и команду его создания. Participant должен быть активен, без активного владельца и зарезервированного Account. Привязка или удаление исходного ресурса прекращают действие доказательства повторного использования. Отмена услуги оставляет право использовать собственный профиль в пределах срока исходного credential.

## PARTICIPANT OWNERSHIP

`promote_guest` требует, чтобы CourseEnrollment и Participant были созданы одной командой. Для Participant с заранее указанным Account дополнительно применяется проверка существующей eligibility. Транзакция привязки сохраняет проверку текущего управления и guard активного владельца. Привязка самой записи к новому или уже управляемому целевому профилю сохраняет ограничения по сроку и Attendance.

## LEGACY CREDENTIAL COMPATIBILITY

Credential исходной записи сохраняет действующие полномочия при подтверждённом происхождении. Старые credentials повторных записей сохраняют доступ к данным услуги, но данные Participant и прогресс из ответа удаляются. Для самоуправления используется исходная запись и действительный исходный credential. Если подтверждение утрачено, варианты восстановления требуют решения владельца продукта и отдельной ручной проверки.

## FINANCIAL SAFETY

Авторизация повторного использования выполняется до изменений Participant, записи, оплаты и резервирования. Ключи и механизм канонической идемпотентности сохранены. Суммы, проводки, Kaspi, Wallet и правила отмены и возвратов используют действующие обработчики.

## PERFORMANCE & COST IMPACT

Успешное повторное использование добавляет точечное чтение исходного Booking или CourseEnrollment и guard активного владельца. Для исходного CourseEnrollment дополнительно читается один Course. Replays проверяют текущий Participant и снова проверяют исходное доказательство при повторном использовании. Гостевой статус для ответа без профиля пропускает Attendance. Частота опроса и расписания фоновых задач сохраняются. Сканирования исторических данных в обработчиках нет.

## DEPLOY IMPACT

Functions — `executeCanonicalCommand`, `executeGuestCanonicalCommand`, `queryCourseEnrollmentReadModels`. Hosting — YES. Firestore Rules, Storage Rules, Firestore Indexes, Config, Secrets, IAM, автоматическая миграция, schedulers и triggers — NO.

Сначала обновить привязку и read model. Затем обновить гостевые команды и Hosting после проверки новых callable. Так проверка привязки действует к моменту выпуска новых гостевых credentials. Старый клиент может создать новый профиль, а повторное использование требует нового клиента с передачей доказательства. Строгий парсер старой вкладки может отвергнуть статус старой повторной записи без профиля до перезагрузки страницы.

## ROLLBACK

Исправлять сервер вперёд с сохранением проверок происхождения. При откате Hosting повторная запись по сохранённому профилю и просмотр статуса старых повторных записей могут потребовать обновлённого клиента. Перед возвратом старой версии серверного кода потребуется отдельное решение о закрытии затронутых гостевых входов.

## RESIDUAL RISKS

Сравнение происхождения выявляет кандидатов для ручной проверки и само по себе не доказывает злоупотребление. Для спорных случаев требуется подтверждение владельца и ручное решение по каждой записи.
